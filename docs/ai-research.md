# AI Research Agent + Experiment Framework

Milestone 7 adds a deterministic-statistics-in, structured-hypothesis-out research pipeline. An AI model proposes trading-strategy hypotheses; it never calculates a P&L or risk number, never generates or runs arbitrary code, and never modifies an existing `StrategyVersion`. Every AI-involved action is audited, every failed attempt is kept, and the only path toward eventual paper trading (`PAPER_CANDIDATE`) is a human-confirmed HTTP request: nothing in this codebase can reach it automatically.

This document is the reference for how the pipeline works. `docs/research-methodology.md` is the governing policy this implementation enforces; read that first if you want the *why* before the *how*.

## Why a DSL, not generated code

The single most important safety property of this milestone: **the AI never writes or generates executable code.** It proposes a `StrategyDefinition`, a small, closed, Zod-validated JSON document (`packages/strategy-engine/src/strategies/strategy-definition.ts`), which a hand-written, deterministic interpreter (`evaluateStrategyDefinition`) evaluates. There is no `eval`, no dynamic `Function` construction, no template that assembles TypeScript from AI output.

The DSL supports exactly four entry-rule types:

- `EMA_CROSS_ABOVE` / `EMA_CROSS_BELOW`: fast EMA crosses above/below a slow EMA
- `CLOSE_ABOVE_EMA` / `CLOSE_BELOW_EMA`: close price is above/below an EMA

A `StrategyDefinition` also carries `direction` (`LONG`/`SHORT`), `atrPeriod`, and `stopAtrMultiplier`/`targetAtrMultiplier` (both bounded to `[0.25, 10]`, and every period bounded to `[1, 500]`; see `STRATEGY_DEFINITION_BOUNDS`, added specifically to block parameter mining via degenerate values like a near-zero stop). All `entryRules` must agree (ANDed) for a signal to fire.

`evaluateStrategyDefinition` is look-ahead-safe by construction: deciding about candle `i` only ever reads `candles[0..i]`, the same discipline `evaluateEmaTrendPullback` already used. This is proven, not just asserted: `strategy-definition.test.ts` has one genuinely signal-producing, hand-verified fixture per rule type, each checked for prefix-invariance (truncating the series after the decision point produces identical earlier signals) *and* future-mutation-invariance (changing later candles to different values never changes earlier signals). An earlier version of this test used a fixture that produced zero signals in both the full and truncated run, making the assertion trivially true regardless of whether the interpreter was actually safe; this was caught and fixed during the milestone's final review (see "Known limitations" below for how that was found).

The registered strategy key for every AI-proposed `StrategyDefinition` is `"ai-generated-dsl-v1"` (a single shared container `Strategy` row; see "Strategy lifecycle" below for why one hypothesis always maps to one `StrategyVersion`, never a fresh one per experiment stage).

## The AIProvider abstraction

`packages/ai-provider` is deliberately isolated: it depends on `@trading-copilot/strategy-engine` (only for `strategyDefinitionSchema`), `decimal.js`, `zod`, and `@anthropic-ai/sdk`, nothing else. No `@trading-copilot/database`, no NestJS, no BullMQ. This means the package that talks to an AI model can never itself hold or compute a financial value from AI-controlled input; `Decimal` values only ever enter it pre-stringified (see `ResearchAgentPromptInput.summary: Record<string, unknown>`).

```typescript
interface AIProvider {
  readonly type: "MOCK" | "ANTHROPIC";
  generateResearchHypothesis(input: ResearchAgentPromptInput): Promise<AIProviderResult<ResearchHypothesisOutput>>;
}
```

**`MockAIProvider` is the default whenever `ANTHROPIC_API_KEY` is unset: this includes every automated test and CI run, unconditionally.** It hash-seeds a structurally-valid-but-meaningless hypothesis from a SHA-256 digest of the input, so identical input always produces byte-identical output with zero network access. Its `rationale`/`statement` text is self-marked as fake ("Generated by MockAIProvider for testing. No real data interpretation occurred.") so a leaked mock hypothesis can never be mistaken for a real research conclusion.

**`AnthropicAIProvider`** is env-gated and real. It calls the Anthropic Messages API with a forced tool call (`tool_choice: {type: "tool", name: "propose_research_hypothesis"}`), whose JSON-schema-shaped input definition mirrors `strategyDefinitionSchema`'s bounds and rule types (kept in sync by hand; a drift here fails safe, since Zod re-validation is the real trust boundary, not the tool schema). The only path AI output takes into the system is `researchHypothesisOutputSchema.parse(toolUse.input)`: a `.strict()` Zod schema that rejects unknown fields and throws on any validation failure, never coerced, never defaulted, never partially accepted.

**A failed or invalid provider response never discards its evidence.** `AIProviderResponseError` carries the raw response, token counts, and `costUsd` (Decimal-computed, the same helper the success path uses) for both failure modes (no `tool_use` block; schema validation failure), so a `FAILED` `AgentExecution` row keeps its full audit trail and still counts against the daily token budget: a schema-invalid response that Anthropic still billed for is not a free way to bypass the budget.

## The `AgentExecution` audit model

Every call to an `AIProvider` is preceded by a synchronously-created `AgentExecution` row (`status: RUNNING`), written by `apps/api`'s `ResearchService.generateHypothesis` *before* the BullMQ job is even enqueued, so the audit trail exists even if the job never starts. `AgentExecutionProcessor` (`apps/worker`) then loads that row, calls `ResearchAgent`, and persists the outcome:

- **On success:** `provider`/`model`/`promptVersion` are overwritten with the values the provider that *actually ran* reports (`this.aiProvider.type`, `result.model`, `result.promptVersion`), never trusting the API process's creation-time guess. The API and worker are separate processes that can have different env configurations (e.g. only one has `ANTHROPIC_API_KEY` set); without this correction, a real Anthropic call could be misattributed to MOCK in the audit trail. This was confirmed as a real, not theoretical, bug by forcing an actual invalid-API-key 401 during the milestone's final review.
- **On failure:** the raw response, token counts, and cost are preserved whenever a billed response exists (either the provider itself rejected an unusable response, or the provider succeeded and a *later* step, e.g. persisting the hypothesis, threw; `AgentExecutionProcessor` holds the result outside its `try` block specifically to cover this second case). A genuine no-response failure (network error, a bug before any provider call) correctly records no fabricated numbers.

`AI_PROVIDER_PROMPT_VERSION` is bumped whenever the *shape* of what a `ResearchAgent` output must be changes in a way that should not silently reinterpret an old `AgentExecution.outputParsed` row, the same role `NOTIFICATION_TEMPLATE_VERSION` plays for notification content.

**Failed `AgentExecution`/`ResearchExperiment`/`ResearchHypothesis` rows are never deleted, hidden from a list endpoint, or excluded from budget accounting.** No delete function exists anywhere on `researchRepository`, confirmed by an explicit test asserting exactly that.

## From summary to hypothesis: what the ResearchAgent sees

`ResearchAgent` (`apps/worker/src/research/research-agent.ts`) is pure orchestration: it serializes a `ResearchDataSummary` (`packages/analytics`) into JSON-safe input (`toJsonSafe`, converting every `Decimal` to a string via `.toString()`, never `.toNumber()`, which would reintroduce floating-point imprecision) and calls the injected provider. It does zero numeric computation itself.

`buildResearchDataSummary` (`packages/analytics/src/research-summary.ts`) is the deterministic, non-AI statistics layer: the ResearchAgent consumes this, never raw candles or millions of trade rows:

- `overall`: the full `TradeAnalyticsMetrics` (trade count, win rate, expectancy, average R, profit factor, MFE/MAE, drawdown, etc.)
- `bySession`/`byTimeOfDay`/`byMarketRegime`/`byDirection`: categorical breakdowns, each bucketed to `"UNKNOWN"` rather than dropping a trade with missing context
- `vwapDistance`/`volumePercentile`/`atrPercentile`: winner-vs-loser-vs-all continuous-variable comparisons

**What the ResearchAgent can and cannot see.** `EnrichedJournalTrade.context` is only populated for a journal trade whose `JournalTrade` had a `setupId` (a `MarketSnapshot`-backed `Setup`): a purely manual journal entry, or any backtest-sourced trade, has `context: null`. This is a real limitation of the data available today, not an oversight: a manually-logged trade was never scored against session/regime/VWAP context at decision time, so there is nothing honest to report.

## The dataset-role pipeline and the final-test reuse safeguard

```
RESEARCH → VALIDATION → FINAL_TEST → WALK_FORWARD
```

`POST /research/hypotheses/:id/experiments` creates a `ResearchExperiment` and its `Backtest` in one transaction, then enqueues the backtest onto the same `BACKTEST_RUN_QUEUE`/`BacktestRunProcessor` that serves `POST /backtests`, no duplicated backtest logic. The experiment moves `QUEUED → RUNNING → COMPLETED | FAILED` alongside its backtest, and on completion advances the hypothesis's `StrategyVersion` forward (never past `WALK_FORWARD`; `PAPER_CANDIDATE` stays human-only):

| Dataset role completes | StrategyVersion advances to |
|---|---|
| `RESEARCH` | `BACKTESTING` |
| `VALIDATION` | `VALIDATION` |
| `FINAL_TEST` | `OUT_OF_SAMPLE` |
| `WALK_FORWARD` | `WALK_FORWARD` |

Every precondition is checked twice: once read-only before any write (fast-fail), and again authoritatively inside the transaction that creates the `Backtest`+`ResearchExperiment` (so a rejection never leaves an orphan `Backtest` row):

- **Stage order.** A stage after `RESEARCH` requires a `COMPLETED` experiment at the immediately-prior stage.
- **Window isolation.** From `VALIDATION` onward, a stage's window must start at or after the latest window end of every *non-FAILED* experiment for that hypothesis, any role, not just the immediately-prior one. This closes a real methodology gap found during the final review: without it, every stage of one hypothesis could reuse the identical dataset window, silently defeating the whole point of staged validation.
- **Holdout.** `FINAL_TEST`/`WALK_FORWARD` windows must start at or after the hypothesis's `sourceDataSummary.sampleWindowEnd`: the data that generated the hypothesis in the first place. Without this, a "final test" could fall entirely inside data the hypothesis had already been shaped by. Skipped only when that value is genuinely null (a zero-trade hypothesis).
- **Final test is not renewable.** At most one non-`FAILED` `FINAL_TEST` experiment may exist per hypothesis, enforced by a real Postgres partial unique index (`ResearchExperiment_hypothesis_final_test_key`, `WHERE "datasetRole" = 'FINAL_TEST' AND "status" <> 'FAILED'`), never a check-then-insert. A genuine infrastructure-failure retry is still possible (`FAILED` rows fall outside the index's scope), but a `COMPLETED` result can never be relabeled `FAILED` to sneak a renewal past this guarantee (`markResearchExperimentFailed` is an atomic conditional update, only ever `QUEUED`/`RUNNING → FAILED`).
- **History is kept.** Deleting a `ResearchHypothesis`/`Backtest` that a `ResearchExperiment` references is refused at the database level (`ON DELETE RESTRICT`), so a `FAILED` row can never be silently erased alongside its parent.

One `StrategyVersion` per hypothesis, reused across every experiment stage (`findStrategyVersionBySourceHypothesis`, only created fresh on the first experiment): `WALK_FORWARD`/`FINAL_TEST` must validate the *exact same* parameters `RESEARCH`/`VALIDATION` tested, or the staged pipeline proves nothing.

## Experiment budgets

`RESEARCH_DAILY_TOKEN_BUDGET` (default 200,000, configurable via env) caps total input+output tokens spent per UTC day across every `AgentExecution`, including failed-but-billed calls. The check runs before any spend is committed: before `createAgentExecution`, before the job is enqueued. A malformed env value **fails closed**: it throws rather than silently disabling the budget (a plain `Number.parseInt` on a malformed value produces `NaN`, and `tokensUsed >= NaN` is always `false` in JavaScript, exactly the kind of silent-bypass CLAUDE.md's determinism rule exists to prevent, so the budget parser is Zod-validated instead).

`RESEARCH_AGENT_JOB_OPTIONS` (`{attempts: 1}`) means a failed AI call is never automatically retried: an LLM call is neither free nor safe to retry blindly. A human triggers a fresh attempt via a new `POST /research/hypotheses/generate` call.

## Reaching `PAPER_CANDIDATE`

`POST /research/hypotheses/:id/strategy-versions/:versionId/mark-paper-candidate` is the only path to `PAPER_CANDIDATE`, and it is human-gated in three independent ways:

1. `markPaperCandidateRequestSchema` requires the request body to carry `confirmedByHuman: z.literal(true)`; nothing else satisfies the schema.
2. It requires a `COMPLETED FINAL_TEST` and a `COMPLETED WALK_FORWARD` experiment to already exist for the hypothesis.
3. It requires `strategyVersionId` to be the *exact* `StrategyVersion` that hypothesis produced (`findStrategyVersionBySourceHypothesis`), not merely some unrelated `StrategyVersion` that independently happens to be `WALK_FORWARD`: this ownership check was a real gap found and fixed during the final review; without it, the two-experiment gate only proved the *hypothesis* had qualifying experiments, never that the *strategy being promoted* was the one those experiments actually tested.

It also re-checks sample-size guardrails (`assertSampleSizeGuardrails`, both a minimum calendar-day span *and* a minimum candidate-setup count, never either alone) over the combined `FINAL_TEST`+`WALK_FORWARD` window specifically (not the full RESEARCH-through-WALK_FORWARD span: an earlier version of this fix included the RESEARCH stage's own window, which would have let a hypothesis borrow training-period trade volume to satisfy a guardrail meant to gate confidence in the held-out evaluation data; a scoped re-review caught that this made the guardrail *easier*, not harder, to pass, and it was corrected).

The transition itself is an atomic conditional update: `status` must currently be `WALK_FORWARD`, following the same `updateMany`-then-recheck pattern established for `closeJournalTrade`/`markScreenshotReady`/`markNotificationSent`. Only once all of this passes does the row change, in the same transaction as its `STRATEGY_VERSION_STATUS_CHANGED` journal event.

**Nothing in this milestone can reach `PAPER_TRADING` or `APPROVED`.** `advanceStrategyVersionStatus` (the automatic, experiment-driven advance described above) has an explicit ceiling at `WALK_FORWARD` and throws if ever called with a later target. `PAPER_CANDIDATE` itself only advances through the human-gated endpoint above. What a real paper-trading integration, live monitoring, and eventual `APPROVED` promotion require is out of this milestone's scope entirely; see `docs/roadmap.md`.

## Known limitations

- **Outcome-based promotion is not implemented.** Every status advance described above (including `markPaperCandidate`'s own preconditions) is *completion-based*, not *outcome-based*: a `COMPLETED` experiment means the backtest ran, not that the strategy passed any performance bar. A strategy with negative expectancy in both `FINAL_TEST` and `WALK_FORWARD` currently qualifies for `PAPER_CANDIDATE` as long as a human confirms it. This is acceptable for this foundation milestone specifically because the human confirmation step exists and is documented here: a future milestone should add recorded acceptance criteria, a distinct `VALIDATED`/`REJECTED` hypothesis outcome, and the robustness checks `docs/research-methodology.md`'s "Overfitting and parameter mining" section already requires (performance by regime/session/direction, sensitivity to slippage/commissions/parameter perturbation) before a strategy can be meaningfully considered for real paper trading.
- **The sample-size guardrail's population is system-wide, not per-experiment.** `assertSampleSizeGuardrails` is checked against every closed journal trade in the system (because `ResearchHypothesis`/`ResearchExperiment` carry no `strategyId`/`instrumentId` column to scope by), not the specific trades a given experiment's own backtest produced. It answers "has the trading system as a whole matured enough to justify a riskier stage," not "did this specific strategy test on enough data." A future refinement would evaluate the guardrail against an experiment's own `BacktestTrade` count once execution completes.
- **`AgentExecution.costUsd` is `DECIMAL(10,4)`,** which rounds a small per-call cost (a true $0.004542 stores as $0.0045). This does not affect budget enforcement (token-based, not cost-based) or any trading math, but summed cost figures drift. A follow-up migration to widen the column's scale is recommended.
- **Application-level stage-order/window-isolation checks are not fully race-proof.** They are read-then-decide checks inside the creation transaction, re-checked authoritatively, but two genuinely simultaneous `createExperiment` calls for the same hypothesis and role could both pass the pre-check before the transaction serializes them. Only the final-test-reuse rule is a hard database constraint. Proven safe for this specific case by a live 5-round concurrent-creation test during the final review (exactly one winner per round, zero orphan `Backtest` rows); the residual risk is bounded to non-final-test stages and is accepted as proportionate for a single-operator platform, matching this project's established risk tier for similar low-frequency, human-driven races (e.g. `Setup.execute()`/`skip()`'s app-level guard).
- **A completion-hook failure with `attempts: 1` has no automatic recovery.** If `BacktestRunProcessor`'s research-completion bookkeeping fails after a backtest genuinely completes (the backtest's own status is never corrupted by this, see the next bullet), the linked `ResearchExperiment` can be left `RUNNING` indefinitely, permanently consuming a hypothesis's `FINAL_TEST` slot with no automatic path back to `FAILED`. A future fix would add a reconciliation sweep, mirroring `WebhookReconciliationProcessor`'s precedent from Milestone 3.
- **A research-bookkeeping failure never corrupts a genuinely-successful backtest.** `BacktestRunProcessor`'s research-completion hook runs *outside* the backtest's own try/catch, specifically so a bug in research bookkeeping can surface as a visible job failure without ever relabeling a `COMPLETED` `Backtest` as `FAILED`.
- **The vacuous look-ahead test was a real gap, now closed and independently re-verified twice.** The DSL's original "is look-ahead-safe" test used a fixture that produced zero trading signals in both the full and truncated series, so its core assertion compared `[]` to `[]` and could never fail, regardless of whether the interpreter was actually safe. This was caught by the milestone's final quality review (which independently ran the evaluator against the fixture and hand-derived the EMA values to confirm it), fixed with genuinely signal-producing, hand-verified fixtures for all four rule types, and the fix itself was proven correct by temporarily injecting a real look-ahead bug into the interpreter and confirming the new tests caught it, twice, independently, by two different reviewers. This is recorded here because it is a concrete example of why "the test passed" is not sufficient evidence on its own; the underlying interpreter was correct throughout, but the proof of that was not, for a period during this milestone's development.
