- **BLOCKER (quant-engineer)**: `closeJournalTrade`'s MFE/MAE candle-range query used `timestamp >= entryTimestamp` - but a candle's timestamp is its OPEN time, and a real-world fill happens *during* a candle's interval, not at its exact open. Free-typed dashboard datetime inputs are essentially never aligned to a candle boundary, so this silently dropped the entry candle: understating MFE/MAE for multi-candle trades, and producing a spurious `null` (masquerading as "no candle data") for fast single-candle trades. The controller's own live-system verification happened to use boundary-aligned timestamps and didn't catch it - exactly the scenario the bug is invisible in. Fixed by resolving the range start to the candle that actually *contains* `entryTimestamp` (`lte`+`desc`+`findFirst`) before querying; also threaded the transaction's `tx` client through the candle read (was previously using the module-level `prisma` singleton, breaking `closeJournalTrade`'s isolation boundary). Two live-Postgres regression tests added with concrete hand-computed expected values, proving both the fix and that the old code would have produced different (wrong) numbers for the same inputs.
- **HIGH (quality-reviewer)**: `execute()`/`skip()` could produce contradictory journal history - even with Task 9's READY-status guard, nothing stopped a second `skip()`, or `skip()` then `execute()` (either order) from both succeeding, leaving one Setup marked both `SKIPPED` and executed. Fixed by broadening the existing double-submit guard (`findJournalTradeBySetupId`, was OPEN-only) to reject either action if the Setup has *any* prior recorded decision - same proportionate app-level-check tier as the existing guard, not a new DB migration.
- **HIGH (quality-reviewer)**: the dashboard displayed `mfe`/`mae` with `formatCurrency` (a "$" prefix), but `calculateExcursions` returns a raw price-point distance, never multiplied by `pointValue`/`quantity` - the same quantity the backtester computes and correctly labels as points on its own trade-detail page. Fixed by switching to `formatDecimal` labeled "points," matching the backtester page's convention. Calculation itself was always correct; this was purely a display-layer unit-mismatch bug.
- **MEDIUM (quality-reviewer, closes a previously-known-limitation)**: `NOTIFICATION_QUEUE` could still strand a row at `RETRYING` forever for a genuinely temporary-but-persistent failure (e.g. a multi-minute Telegram outage) - Task 7's `SetupContextNotFoundError` fix only closed the deterministic-permanent-failure case. Fixed: the processor now checks `job.attemptsMade` against the job's configured `attempts` and routes to `FAILED` (`RETRY_ATTEMPTS_EXHAUSTED`) on the last attempt instead of `RETRYING`.
- **MEDIUM (quality-reviewer)**: `TelegramNotificationProvider`'s `fetch()` calls had no timeout, so a hung connection could block a worker slot indefinitely. Fixed with `AbortSignal.timeout(10_000)` on both `sendMessage`/`sendPhoto`.
- **MEDIUM (journal-analyst)**: `TRADE_SKIPPED`/`TRADE_EXECUTED`/`TRADE_CLOSED` journal events carried no metadata, so a reader given only the JournalEvent stream couldn't tell *why* a trade was skipped or *what* it closed as without a second query. Fixed by adding real metadata (`skipReason`, `actualEntry`/`quantity`, `outcome`/`netPnl`/`rMultiple`) to all four emission sites.

All five fixes independently re-reviewed or controller-verified clean; final `pnpm lint`/`typecheck`/`test`/`build` re-run clean after every fix landed.

## Known limitations (Milestone 6)

- `execute()`/`skip()`'s "any prior decision" guard (`findJournalTradeBySetupId`, checked before create) is not inside a database transaction spanning both the check and the create, so it does not close a true microsecond-level concurrent race - only a double-click, an HTTP retry, or a skip/execute ordering conflict from sequential real-world use. Judged proportionate because both endpoints are only ever called by a human clicking a dashboard button, not an automated caller; a complete fix would need a partial unique database index (e.g. `UNIQUE (setupId) WHERE status IN ('OPEN','PLANNED','SKIPPED')`), out of this milestone's scope.
- `POST /setups/:id/execute` and `/skip`, like every other internal API route in this codebase, have no authentication or authorization layer. Consistent with this project's existing documented posture (a personal, single-user tool) - not a new gap introduced by this milestone, but worth restating here since these two endpoints record real trade decisions.
- `closeJournalTrade`'s `OPEN→CLOSED` transition is a pre-existing (Milestone 2) check-then-act read/update, not the atomic conditional-`updateMany` pattern this milestone uses everywhere else for exactly this reason - two concurrent `POST /journal/trades/:id/close` calls (e.g. two browser tabs) could race. Not introduced by Milestone 6, but now more reachable via the new `CloseTradeCard` dashboard button. Recommended fast-follow: the same atomic-`updateMany` guard already used by `notification-deliveries.ts`/`trade-screenshots.ts`'s `mark*` functions.
- `packages/database/src/repositories/trade-screenshots.ts`'s `requestOrRetryScreenshot` (Milestone 5, unmodified by Milestone 6) has the identical unguarded-`FAILED`-retry-reset race that Task 4 found and fixed for `requestOrRetryNotification` in this milestone - confirmed by the final system-architect review to be genuinely out of Milestone 6's diff. Recommended fast-follow: apply the identical `updateMany`-with-status-guard fix.
- **Discovered, genuinely pre-existing (Milestone 1/2), out of this milestone's scope**: `apps/dashboard/src/components/AnalyticsStatGrid.tsx` displays "Avg MFE"/"Avg MAE" via `formatCurrency`, but `packages/backtester`'s own `maximumFavorableExcursion`/`maximumAdverseExcursion` (which feed that average alongside this milestone's own points-denominated `JournalTrade.mfe`/`mae`) are also raw, unmultiplied price-point distances - the same unit-mismatch bug this milestone fixed on the single-trade Journal page, but on the Analytics page's aggregate view instead. Confirmed via diff that `packages/analytics` and `AnalyticsStatGrid.tsx` are completely untouched by this branch. Recommended fast-follow: the same `formatDecimal`-as-points fix, applied to `AnalyticsStatGrid.tsx`.

## Known limitations (Milestone 5)

- `/internal/render/setup/[setupId]` and `/internal/render/trade/[tradeId]` have no runtime authorization beyond "not linked from navigation" — consistent with the rest of the dashboard, which has no auth model anywhere today. Before any deployment reachable beyond localhost, these routes need network-level or auth protection (a shared-secret header or IP allowlist in Next.js middleware, verified by the worker's `page.goto` call).
- A screenshot row stuck at `GENERATING` (e.g. the worker process crashes mid-render) has no automatic recovery path — only `FAILED` rows are recoverable via retry. Out of scope for this milestone; would need either a stale-`GENERATING` sweep or a render-attempt timeout.

## Known decisions

- `Candle.timeframe` and `Backtest.timeframe` are plain `String` columns validated against `TIMEFRAMES`, not Prisma enums — Prisma enum values must be valid identifiers and values like `"1m"` are not.
- Same-candle stop-and-target ambiguity resolves to "stop hit first" (see `docs/backtesting-assumptions.md`).
- Entry timing is next-bar open after a signal candle's close, to prevent look-ahead bias.
- Test runner is Vitest across every package and app for a coherent toolchain, including the NestJS apps (`@nestjs/testing` has no Jest-specific dependency).
- BullMQ queue name `"backtest-run"`, job name `"run"`, payload `{ backtestId }` only — the worker re-fetches everything else from Postgres so the job payload never goes stale relative to the DB.
- Same-candle stop-and-target exits apply the same adverse slippage as a plain STOP exit, for consistency (fixed after an initial pass omitted it).
- `initialBalance`, `tickSize`, `tickValue`, `pointValue` reject a zero value at the API/schema boundary (synchronous 400) rather than only failing later inside `packages/risk-engine`; `commissionPerContract` and `riskPercentage` still legitimately allow zero. `POST /backtests` also rejects `startDate >= endDate`.
- The dashboard's Research pages show a persistent banner noting the synthetic data and untuned strategy parameters, so that context isn't only discoverable in `docs/`.
- `JournalTrade` is intentionally distinct from `BacktestTrade` — never duplicated into it. `packages/database`'s `getNormalizedTrades()` merges both in memory at query time for `packages/analytics`.
- `JournalEvent.eventType`/`entityType` are real Prisma enums (stronger DB-level validation), not plain strings, unlike `Candle.timeframe` — their value sets don't start with digits, so the Prisma-enum-identifier problem that forced `timeframe` to be a string doesn't apply here.
- Every event in a `Setup`'s lifecycle (including its `JournalTrade`'s) shares `correlationId = setup.id`, making `GET /setups/:id/timeline` a single indexed query rather than a cross-table join.
- A `plannedRisk` of exactly `"0"` on a `JournalTrade` is treated identically to `null` (no risk baseline) at close time — `rMultiple` is `null`, never a thrown error or a fabricated `0` (a caller can't distinguish "unset" from "typed zero" through the API, so both get the same safe handling).
- `NestJS`'s `@UsePipes` at the method level applies to *every* parameter, not just `@Body()` — any handler combining `@Param()` with a Zod-validated body must apply `ZodValidationPipe` at the parameter (`@Body(new ZodValidationPipe(schema))`), not the method, or the path param gets incorrectly validated against the body schema too.
- `getNormalizedTrades()` sorts its merged output by `entryTimestamp` (both source queries are also individually ordered, but concatenating two sorted lists doesn't itself produce a globally sorted one) — `packages/analytics` never re-sorts, so this is the only place ordering can be guaranteed.
- `createPostTradeAnalysis` verifies the referenced `BacktestTrade`/`JournalTrade` exists before inserting (404 via `NotFoundError` otherwise) — the only integrity check available for a polymorphic reference that can't have a real database foreign key.
- `createStrategyVersion` emits `STRATEGY_VERSION_PROPOSED` in the same transaction as the create — no `StrategyVersion` row exists without a corresponding journal entry.
- `/analytics` and its strategy-version detail page carry an `AnalyticsDisclaimer` banner (mirroring `/research`'s `ResearchDisclaimer`) since a single row can blend simulated backtest trades and real/paper journal trades — check the trades table's `Source` column before treating a number as evidence about live performance.
- `InboundWebhookEvent.fingerprint` excludes `firedAt` (wall-clock delivery time) and the OHLCV fields from its canonicalized input, keyed only on `provider/strategyKey/strategyVersion/exchange/symbol/timeframe/signal/direction/barTime`. A genuine retry of the same trigger can have a different `firedAt`, and including OHLCV would make the fingerprint fragile to harmless formatting differences between deliveries of the same bar.
- Instrument and strategy resolution for a TradingView webhook never guess: an unmapped `exchange`/`symbol` is `UNKNOWN_INSTRUMENT`, an unmatched `strategyKey`/`strategyVersion` pair is `UNKNOWN_STRATEGY_VERSION` (never "fall back to latest version"), both rejected with the `InboundWebhookEvent` row kept for audit, never silently dropped.
- `Setup.sourceWebhookEventId` (nullable, `@unique`) is the idempotency guard against a BullMQ retry creating a second `Setup` for one webhook delivery: the same "database constraint, not check-then-insert" principle as `fingerprint`, added after a review found the original retry-safety logic checked only `InboundWebhookEvent.processingStatus`, which is insufficient on its own (a crash between `createSetup` and the event being marked `PROCESSED` leaves it at `PROCESSING`/`FAILED`, neither of which blocks reprocessing).
- The setup-expiration BullMQ job is scheduled *before* the `InboundWebhookEvent` is marked `PROCESSED`, not after. Marking `PROCESSED` blocks any future retry, so scheduling first means a crash between the two steps just means a retry (or the sourceWebhookEventId recovery path) schedules the expiration job again, which is harmless, rather than the job never being scheduled at all.
- A synchronously-`400`-rejected webhook delivery (envelope-invalid, or `schemaVersion: 1` but the full v1 shape is invalid) is still durably persisted as `REJECTED`/`MALFORMED_PAYLOAD`, using a fallback fingerprint (a hash of the whole raw body, since the real field-based fingerprint needs specific fields to exist and parse). The HTTP response stays an unchanged, fast, synchronous 400.
- `WebhookProcessingStatus.DUPLICATE` is a reserved enum value, never actually set by any code path: a repeat delivery never gets its own row, and the original row's status is deliberately never overwritten (doing so would incorrectly imply an already-successful delivery was invalidated). "This was redelivered" is conveyed instead via the `wasDuplicate` response flag and a `WEBHOOK_DUPLICATE_DETECTED` journal event.
- `apps/api`'s and `apps/worker`'s `dev` scripts use `tsc --watch` + `node --watch dist/main.js`, not `tsx watch`. `tsx` transpiles via esbuild, which does not emit the TypeScript decorator metadata NestJS's dependency injection depends on for implicit constructor-based injection, so any such provider silently read as `undefined` at request time under the old script.
- `NotificationDelivery.failureCode`/`failureMessage` are always drawn from a small, fixed, known set (`classify()` in `telegram-notification.provider.ts`, plus the processor's own `SETUP_NOT_FOUND`/`SETUP_CONTEXT_NOT_FOUND`/`UNKNOWN_ERROR`), never the raw provider error text - a Telegram error response could in principle echo request details, including the bot token, back in its description.
- `isTelegramConfigured` (the three-env-var Telegram-configured check) has exactly one implementation, in `packages/shared-types/src/notifications.ts`; `apps/worker`'s `notification-provider.factory.ts` re-exports it rather than duplicating it, after an integration pass found Tasks 5 and 10 had independently landed byte-identical duplicate implementations.
- `JournalTrade.mfe`/`mae`/`outcome` cannot be set through the API at all as of Milestone 6: `closeJournalTradeSchema` has no such fields, and both are computed inside `closeJournalTrade` itself. A `JournalTrade` with no `Setup` lineage (`setupId: null`) gets `mfe: null`/`mae: null` (no timeframe to know which candle series to query) - this is expected, not a bug.
- `POST /setups/:id/execute`'s `plannedStop` fallback to `plannedEntry` (when the `Setup`'s own `plannedStop` is `null`) is genuinely load-bearing, not dead code: `transitionSetupStatus`'s transition matrix has no precondition requiring `plannedStop`/`plannedTarget1` to be non-null before a `Setup` can reach `READY`, so a `TRADINGVIEW`-sourced setup can legitimately be `READY` with only a candidate entry known. Confirmed live against a real `READY` setup with `plannedStop: null` during Task 9's review.
